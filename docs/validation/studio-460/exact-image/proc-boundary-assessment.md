# Read-only proc-boundary assessment

Current image: manifest sha256:e56e7028a265aa550d51fb19991ff889d400c262f2c31f7182f58814b3a77d70. Build, native startup accepting mounted finite-limit files whose correspondence to actual process membership was unproven, and renderer/Chromium/codec resolution passed. Actual signed rendering failed before child code, at Bubblewrap's fresh proc mount. No proc exposure experiment, outer mask removal, supervisor-proc bind, host policy change or redesign has been performed.

## Observations and limits

The live supervisor has Seccomp0, zero effective/permitted capabilities, NNP1 and AppArmor `chatgpt (unconfined)`. No matching kernel audit entry was returned. The child clone creates private user/PID/net/mount namespaces; tmpfs and read-only binds succeed; mounting proc fails EPERM. Linux v7.0 upstream fs/namespace.c checks existing proc visibility and rejects locked child mounts covering nonempty entries. This is strong evidence for visibility rejection; no kernel-branch instrumentation proves the exact branch on Ubuntu7.0.0-31.

Primary source: https://raw.githubusercontent.com/torvalds/linux/v7.0/fs/namespace.c (mnt_already_visible, mount_too_revealing). https://raw.githubusercontent.com/torvalds/linux/v7.0/fs/proc/root.c still applies SB_I_USERNS_VISIBLE to proc, including subset=pid; subset alone is not an established escape from that check here.

## Does the current image preserve every mask?

The image itself does not define OCI masks. This test's OCI spec preserves its default outer maskedPaths: /proc/acpi, /proc/asound, /proc/kcore, /proc/keys, /proc/latency_stats, /proc/timer_list, /proc/timer_stats, /proc/sched_debug, /proc/scsi, /sys/firmware. It also preserves readonlyPaths /proc/bus, /proc/fs, /proc/irq, /proc/sys, /proc/sysrq-trigger. Actual mount evidence is retained. No untrusted child ran after the failure.

However, the intended inner recipe cannot be described as independently reproducing every outer mask. Pinned Bubblewrap0.11.1 bubblewrap.c SETUP_MOUNT_PROC creates a fresh child proc then conditionally read-only covers sys, sysrq-trigger, irq and bus. It does not recreate all OCI masked proc entries or explicitly cover /proc/fs; /sys is absent in the inner filesystem, so /sys/firmware is absent. Unix permissions and seccomp do not substitute for an asserted complete mount-mask policy. Historical native host render proof is not proof of full OCI-mask equivalence.

## Can the existing supervisor simply mount before masking the child?

The current Bubblewrap path already mounts its private proc before its own conditional proc restrictions and before sandbox-init/untrusted code. Its parent OCI proc is already masked, and the new user/mount namespace inherits locked mounts. Reordering only child masking therefore does not resolve the observed earlier denial. The existing native entrypoint starts UID1000 without effective capabilities, creates its own user namespace, mounts bounded /work, and drops capabilities before Node. Retaining CAP_SYS_ADMIN only in that child user namespace would not bypass the proc-visibility check. Granting initial-host-user-namespace CAP_SYS_ADMIN would be a much broader authority and is not proposed.

## Smallest sequencing candidate to assess, not an implemented solution

A trusted credential-free bootstrap would need a platform-provided point BEFORE the outer proc masks are locked into the execution mount namespace (or a separately authorized trusted bootstrap mount namespace). At that point it could create a job-only PID namespace and mount its own proc at a fixed private staging path, apply all existing applicable masks/read-only restrictions, then expose that proc only at the job's /proc. A fixed job init must keep that namespace alive; authored processes must join that exact PID namespace. No mount of the API supervisor's proc is acceptable: child /proc/1 must refer to job init, never API Node or an outside broker. Masks must be applied and independently checked before authored code, and all capabilities dropped/NNP/seccomp installed afterward. Input stays the exact readonly /input; runtime resources remain fixed image paths; scratch and resource bounds stay unchanged.

A one-job-per-instance bootstrap could retire rather than reuse a precreated namespace, but that changes lifecycle/dispatch and needs proof. Keeping an unmasked helper namespace indefinitely changes outer trusted exposure and is not silently equivalent. Merely preserving an O_PATH proc FD after masking is not evidence that the kernel considers the mount fully visible. No such option has been demonstrated here.

Required platform capability is deferred outer masking or a trusted prestart/bootstrap hook plus subordinate user/PID/mount namespace control, scoped CAP_SYS_ADMIN during trusted setup only, and inherited enforceable cgroups. Ordinary intended Railway service support for that ordering is not established. This is a concrete capability question, not a claim that external per-job OCI is required or deployable. Existing masks remain intact pending review; no implementation/exposure change is authorized by this assessment.

Candidate acceptance must inventory existing masked files and directories separately: file masks must remain non-disclosing fixed masks, directory masks must remain empty and read-only, and /proc/bus,/proc/fs,/proc/irq,/proc/sys,/proc/sysrq-trigger must retain the required read-only behavior. Validate actual child mountinfo and read/write results, not only an argument list. Prove no ancestor supervisor PID, /proc/<ancestor>/root, fd or mem access; job-private proc must correspond to the same PID namespace used by authored processes. After dropping setup authority, attempted mount/remount/umount/pivot_root/setns/new-user-or-PID-namespace operations must fail, including attempts to uncover masks. Retain exact mask/PID/capability/NNP/seccomp evidence before any code executes and adversarial checks afterward. These are required tests, not results already obtained.
