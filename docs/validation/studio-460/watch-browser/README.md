# Built Watch playback and permanent revocation — local protocol evidence

The production Manager browser saved and enqueued a five-second text composition. Real contained Chromium execution, independent codec verification and canonical retention completed. The durable Mux adapter consumed one intent against an owned loopback protocol fixture, received signed-only readiness and staged the hidden catalog release. Browser review, trusted interactive approval, fresh readiness and atomic publication then succeeded.

The built Watch page loaded the canonical poster and played master → variant → TS through opaque canonical resource URLs. Video readyState was 4 and currentTime advanced beyond one second. No Mux signing token was exposed to the browser. The local protocol fixture validates the server-generated RSA token and serves HLS generated from the actual retained MP4; this is **not actual Mux acceptance**.

Before unpublish, poster, master, variant, TS, storyboard VTT and rewritten storyboard image requests succeeded with `private, no-store, max-age=0`. HEAD returned 200 with zero body bytes. A TS range request returned 206 and exactly 188 bytes, `bytes 0-187/241016`.

The Manager's actual permanent-unpublish control locked the project. All six already-issued URLs subsequently returned 404 with no-store headers. The original Watch page remained open: its stale poster reference returned 404, and clicking its original Watch-now button caused a canonical playback request returning 404. Browser page errors were empty. Previously delivered bytes cannot be recalled; this proof concerns subsequent requests.

Fixture qualification and retained failures:

- The first published fixture used a UUID language slug. It has a valid canonical snapshot, but Watch's public language classifier rejects that slug. It remains unchanged and is not presented as successful Watch playback.
- The qualified fixture uses the supported `english` inventory slug and BCP-47 `en`, with a distinct owned Language row and canonical project.
