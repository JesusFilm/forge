# Stale file-lock recovery must also recover its transition guard

## Problem

The RAG source-status and dashboard publication commands use a shared file lock.
Stale-lock recovery initially protected its destructive transition with a guard,
but that guard could itself be abandoned after a crash. Recovery also needed to
avoid acting on a successor lock installed after the original stale observation.

## Symptoms

- Before guard recovery was added, a command could time out waiting for a
  transition guard even though no useful operation was running.
- Without an identity recheck, recovery of an old valid lock could remove a
  newer valid lock acquired by another process.
- Before the ignore contract was corrected, lock residue could appear in Git
  status because the rules described a different file or directory shape than
  the implementation created.

## What Didn't Work

- An unowned transition-guard directory made the recovery path non-recoverable:
  a process could create the directory and die before completing its critical
  section, leaving later callers to see only `EEXIST` until timeout.
- Checking that a lock was stale before acquiring the guard was insufficient.
  Another process could replace the lock between observation and quarantine.
- Broad or guessed ignore patterns did not prove that the exact lock, guard, and
  quarantine artifacts produced by the implementation were ignored.

## Solution

Use an owner-aware protocol for both the primary lock and its transition guard.
Each carries a random ownership token, process ID, and creation time. A caller
may quarantine an aged guard only when its owner metadata is absent or invalid,
or its recorded owner process is no longer live. A live owner remains protected
even when the guard is old.

For a stale primary lock, record its observed identity, acquire the transition
guard, and read the lock again. For valid metadata, quarantine it only when the
second observation still carries the same owner token. Unparsable stale locks
are recoverable but do not provide this per-owner identity guarantee. Release
also checks the stored token, so an old valid owner cannot remove a replacement
lock. The defining implementation is
`apps/rag/scripts/lib/owned-file-lock.ts`.

Tests in `apps/rag/tests/source-status-cli.test.ts` exercise the three critical
cases: abandoned-guard recovery, refusal to recover an aged guard owned by a live
process, and preservation of a successor lock inserted after the stale read.
The ignore contract in `apps/rag/.gitignore` names the actual regular lock files,
guard directories, and quarantine paths generated by the protocol.

## Why This Works

Exclusive file creation selects one lock owner. The transition guard serializes
the stale-check and rename, while its own owner record allows later callers to
recover that serialization mechanism after a crash. Rechecking the primary
owner token under the guard closes the time-of-check/time-of-use gap for valid
owned locks: recovery can delete only a lock carrying the token it originally
classified as stale. Token-matched release provides the same protection during
normal cleanup.

## Prevention

- Treat recovery as a state transition with its own crash-recoverable ownership
  record, not as a best-effort removal.
- Recheck the exact owner identity after acquiring the recovery guard and before
  moving a stale path.
- Test abandoned recovery state, live-owner exclusion, and a deterministic
  successor-replacement interleaving.
- Assert ignore behavior against the exact regular-file and directory paths the
  implementation creates, including quarantine variants.
