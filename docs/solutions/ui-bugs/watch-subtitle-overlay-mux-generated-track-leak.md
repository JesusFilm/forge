# Watch subtitle overlay rendered Mux generated tracks that the Forge modal did not offer

## Problem

`/watch/jesus.html/english.html` had no admin-backed English subtitle option
in the Forge subtitles modal, but the player could still render English
captions. The page's Mux HLS manifest exposed a native English text track
named `Generated subtitles`, and `SubtitleOverlay` treated any active
`subtitles` or `captions` track as eligible overlay input.

The modal and overlay were therefore using different authorities:

- The modal used admin `VideoEdition.subtitles`, normalized into
  `WatchVideoRecord.subtitles`.
- The overlay used the browser media element's `TextTrackList`, which can
  include Mux-native generated tracks that Forge did not offer to the user.

## Symptoms

- The Language & Subtitles modal showed English audio and only the subtitles
  off switch, with no selectable English subtitle row.
- Browser inspection of the page showed a native media text track:
  `kind: "subtitles"`, `label: "Generated subtitles"`, `language: "en"`.
- Because `SubtitleOverlay` only checked track kind and active mode, a native
  Mux track could render through the Forge overlay if it became active.

## What Did Not Work

- Relying only on `HeroPlayer` to disable built-in tracks is not enough. Mux can
  add or reactivate native tracks after metadata loads, and overlay correctness
  should not depend on winning every player-side timing race.
- Treating all active `subtitles` or `captions` tracks as equivalent is the
  wrong API boundary. Browser media tracks are playback implementation state;
  the Forge modal is product state.

## Solution

Make the Forge-injected subtitle track identifiable and require that identity
inside `SubtitleOverlay`.

`HeroPlayer` already injects the selected VTT track with the internal label
`__forge_subtitle__`. The fix moves that label into a shared watch-local
constant and makes `SubtitleOverlay` require it:

```ts
export const FORGE_SUBTITLE_TRACK_LABEL = "__forge_subtitle__"
```

```ts
const track = tracks.find(
  (t) =>
    (t.kind === "subtitles" || t.kind === "captions") &&
    t.label === FORGE_SUBTITLE_TRACK_LABEL &&
    (t.mode === "showing" || t.mode === "hidden"),
)
```

The overlay still hides the Forge track before rendering React cue text, but it
ignores Mux-native tracks such as `Generated subtitles` even if those tracks are
`showing` or `hidden`.

Regression coverage should use a minimal jsdom `TextTrackList` harness:

- active Mux-generated subtitle track is ignored and left in its current mode;
- Forge-labeled track renders active cue text and gets hidden for custom
  overlay rendering;
- switching from a Forge track back to only native/generated tracks clears stale
  overlay text.

## Why This Works

The user-facing subtitle state is the Forge modal selection, not every subtitle
track that Mux or the browser knows about. Filtering by the internal Forge
track label makes overlay rendering follow the same source of authority as
`WatchPageClient` and `LanguagePickerModal`.

This also keeps Mux metadata, chapter, thumbnail, and generated subtitle tracks
available to the media stack without letting them become product-visible
subtitle choices.

## Prevention

- Do not derive Forge subtitle overlay state from generic media text-track
  kind/mode alone.
- Any future custom overlay should require a Forge-owned identity marker on the
  track it consumes.
- Browser proof for subtitle bugs should inspect both surfaces: the modal
  options and the media element `TextTrackList`.
