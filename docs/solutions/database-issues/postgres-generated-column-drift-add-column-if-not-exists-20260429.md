## Problem

PostgreSQL's `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` guard checks the
column **name**, not its **definition**. If a future change edits a
generated column's expression (e.g. swaps `to_tsvector('simple', ...)` for
`to_tsvector('english', ...)`), every database that already has the column
silently keeps the stale expression. Idempotent on-boot bootstraps that
re-run on every deploy will not detect or correct the drift.

## Symptoms

- A search retriever's WHERE clause references a tsvector that "should"
  match the indexed expression but the planner uses a Seq Scan.
- `\d videos` shows the column with the new name and right type, but
  `pg_get_expr(adbin, adrelid)` for the column shows the old expression.
- Test data ingested on the new code looks correct in feature tests
  (because the tsvector is regenerated by the _current_ expression at
  insert time), but rows ingested before the deploy keep the _old_
  expression's output.

## What Didn't Work

- Trusting `ALTER TABLE ... ADD COLUMN IF NOT EXISTS title_tsv tsvector
GENERATED ALWAYS AS (...) STORED` to upgrade the expression on the
  next deploy. It silently no-ops on the column-name match.
- Asserting the bootstrap SQL string contains the new expression in a
  unit test. The unit test passes; production still has the stale
  generated column.

## Solution

Treat any change to a generated-column expression as a **breaking
schema change** that requires an explicit migration step. The bootstrap
must drop the column with `CASCADE` (the generated column has GIN-index
dependents) before re-running the idempotent `ADD COLUMN IF NOT EXISTS`:

```sql
-- Before changing the generated expression:
DROP INDEX IF EXISTS videos_lexical_weighted_idx;
ALTER TABLE videos DROP COLUMN IF EXISTS title_tsv;
ALTER TABLE videos DROP COLUMN IF EXISTS description_tsv;

-- Bootstrap then re-creates with the new expression.
```

In the bootstrap module, document the trap inline so the next maintainer
knows the IF NOT EXISTS guard isn't a free pass:

```ts
/**
 * **Generated-column expression drift**: `ADD COLUMN IF NOT EXISTS` is
 * column-NAME-aware, not expression-aware. Any change to
 * TITLE_TSV_GENERATED_EXPR REQUIRES an explicit DROP COLUMN ... CASCADE
 * migration step before this bootstrap re-creates the column. There is
 * no automated drift detection.
 */
```

## Why This Works

PostgreSQL's `IF NOT EXISTS` only avoids "column already exists" errors;
it doesn't reconcile the new definition against the existing one. The
column's generated expression is stored in `pg_attrdef` at column-create
time and is immutable after that — there's no `ALTER COLUMN ... SET
GENERATED AS` syntax. Dropping the column drops the `pg_attrdef` row;
re-adding it stores the current expression.

The drift is invisible because:

- `\d` only shows column type, not expression
- The expression evaluates correctly for _new_ rows on every insert/update
- Existing rows keep their precomputed (stale) tsvector value until the
  row is rewritten

## Prevention

1. **Test for drift, not just shape.** Write an integration test that
   reads `pg_get_expr(adbin, adrelid)` for the generated column and
   asserts byte-equality with the TS constant:

   ```sql
   SELECT pg_get_expr(adbin, adrelid)
   FROM pg_attrdef d
   JOIN pg_attribute a ON a.attrelid = d.adrelid AND a.attnum = d.adnum
   WHERE a.attrelid = 'videos'::regclass AND a.attname = 'title_tsv';
   ```

2. **Document the trap at the call site.** The bootstrap module's
   docstring should warn that any expression edit requires a
   coordinated DROP COLUMN step.

3. **Code-review checklist for bootstrap modules.** When reviewing a PR
   that edits a generated-column expression, require an explicit
   migration step (or an out-of-band DROP COLUMN runbook entry) — not
   just the IF NOT EXISTS DDL.
