## Problem

`/watch/jesus.html/blang.html` 404s because `packages/watch-url-policy/src/public-watch-language-slugs.ts`
(a static allowlist gating `apps/web/src/lib/locale.ts:215` `isPublicWatchLanguageSlug()`) doesn't
contain `"blang"`. This file and its sibling `apps/web/src/lib/language-bcp47-map.ts` were frozen on
2026-05-28 and never regenerated against admin's live `Language` table, even though admin's data has
kept moving via `core-sync`. The real generator script referenced in both files' header comments does
not exist in the repo (out of scope to rebuild here — tracked separately as feat-337). This ticket is a
quick, manual patch to unblock affected languages now.

## Entry Points

1. `apps/web/src/lib/language-bcp47-map.ts` — `LANGUAGE_BCP47_MAP`, autogenerated slug → BCP-47 map.

   compact slug-only corpus consumed by `isPublicWatchLanguageSlug()`.

5. `packages/watch-url-policy/src/index.test.ts` — coverage for the corpus package.

## Resolution

**blang (the named bug):** Confirmed via the core GraphQL API
(`https://api-gateway.central.jesusfilm.org/`), `language(id: "139769", idType: databaseId)` returns
`bcp47: "blr"`, `slug: "blang"`. Independently re-confirmed the language has live public video content
by querying the JESUS video (`1_jf-0-0`) `variantLanguagesWithSlug`, which returns
`{ slug: "jesus/blang", language: { id: "139769", bcp47: "blr", slug: "blang" } }`. Added
`blang: "blr"` to `language-bcp47-map.ts` and `blang` to `public-watch-language-slugs.ts`.

**Broader drift audit — what was actually possible in this sandbox:** No `apps/admin` Postgres or local
admin GraphQL server was reachable here (no `apps/admin/.env`, no local admin dev server, admin's own
DB not provisioned in this devcontainer). Two things _were_ reachable and used as evidence:

1. The public core GraphQL API (`https://api-gateway.central.jesusfilm.org/`) — same production data
   surface `apps/web` ultimately traces back to via `core-sync`.
2. A local Postgres (`db` host) that turned out to hold `core`'s own per-service `languages` database
   (`Language` table with `id`, `bcp47`, `iso3`, `slug`, `hasVideos`) — **not** `forge`'s admin Postgres.
   This is a leftover dev database from a different repo's devcontainer session, not something
   provisioned for `forge`/admin.

That local `languages` DB was used only as a lead-generation source (candidate slugs + ids), never as
ground truth, because it proved demonstrably stale/incorrect against the live API on multiple points:

- `blang` itself reads `hasVideos: false` in the local DB, contradicted by the live video-variant
  evidence above.
- id `3122`'s slug in the local DB is `banda-mid-southern`; live, the same id's slug is `yakpa-1` — an
  entirely different language name. Slugs get renamed/consolidated in production after the local
  snapshot was taken.
- Several other candidates' `bcp47` values were dirty in the local snapshot (e.g. `fuzhounese-fujianese`
  read `"cdo/"` locally vs the clean `"cdo"` live) or missing entirely (`klingon` had no `bcp47` locally
  but resolves to `"tlh"` live).

Given that, every candidate slug was **re-verified against the live core API by id** (slug, bcp47,
`hasVideos`) before being added — local-DB-only values were never trusted or written into the repo.
`Language.hasVideos` itself is not fully reliable (it under-reports: `blang` is proof of a live-playable
language reading `hasVideos: false`), so it was used only as a supporting **positive** signal, not a
strict gate — entries were included when the _live_ API confirmed a matching slug/bcp47 **and**
`hasVideos: true` at the same id.

completely different live slug, `yakpa-1`, which was never independently identified as missing and
so was not investigated further) and `lala` (already present in the repo under one of its two
colliding admin ids — a pre-existing upstream duplicate-slug data issue, out of scope here).

**Caveat, per this ticket's original ask:** this is still not a full audit against `forge`'s own admin
Postgres/GraphQL — that surface was unreachable in this sandbox. The above is the best achievable
verification path (live core API, cross-checked per-candidate, no local-DB-only values trusted) but
should be re-verified against admin's actual `Language` table once reachable, and ideally superseded
entirely once feat-337 (rebuilding the real generator script) ships.
