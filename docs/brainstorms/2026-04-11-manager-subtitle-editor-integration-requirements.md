# Manager Subtitle Editor Integration

## What We're Building

Add a human subtitle review surface to Forge Manager that can:

- load autogenerated subtitle artifacts from existing enrichment jobs
- let editors adjust cue timing and text while watching the video
- save reviewed subtitle output back into Forge in a durable way
- optionally publish reviewed output back to downstream systems like Mux and CMS

This is not a new subtitle generation pipeline. Manager already generates and stores subtitle artifacts. The gap is the human review and save-back contract between those generated artifacts and the systems that ultimately serve subtitles.

## Why This Approach

### Approach A — Separate Forge-hosted internal editor app (recommended)

Fork `laubonghaudoi/subtitle-editor` into Forge as a dedicated internal editor app, opened from Manager with a signed edit session.

**Pros**

- fastest way to get a capable subtitle UX with waveform, timing edits, and multi-track support
- keeps upstream app assumptions contained instead of forcing them directly into Manager
- clean boundary: Manager handles auth, job/artifact state, save APIs, and publish actions

**Cons**

- needs a small session/load/save adapter layer
- introduces one more internal app to host and maintain

**Best when:** the goal is least painful delivery of human review without rebuilding subtitle editing from scratch.

### Approach B — Embed a forked editor directly inside `apps/manager`

Pull the editor internals into Manager and refactor them into Manager-native routes/components.

**Pros**

- single app shell
- no cross-app navigation or separate deployment surface

**Cons**

- more integration pain up front
- upstream editor is a full Next/PWA app, not a clean reusable component
- higher risk of style, dependency, and routing churn inside Manager

**Best when:** long-term product direction is a large editor workspace fully inside Manager and the team is willing to pay the refactor cost now.

### Approach C — Build a custom Manager editor from scratch

Reuse Forge VTT utilities and artifact routes, but build a new subtitle editor UI tailored to Manager.

**Pros**

- perfect fit for Forge data contracts and workflows
- no fork maintenance

**Cons**

- highest build cost
- recreates waveform, timing, keyboard, and multi-track behavior that already exists upstream

**Best when:** existing editor ergonomics are not a fit, or Forge needs a very opinionated editorial workflow soon.

## Recommendation

Use **Approach A** first: a **Forge-hosted fork as a separate internal editor app**, controlled by Manager.

This is the least painful path because:

- the external editor is MIT licensed and already solves the hard interaction layer
- it is intentionally front-end-only, which makes it forkable
- it is still a standalone app today, with file-based load and download-based save, so using it unchanged or trying to import it directly into Manager would create more friction than value
- Manager already has the right seams for artifacts, auth, and deliberate publish actions

## Key Decisions

- **Manager remains the orchestration layer.** It should own auth, job lookup, artifact access, save APIs, and publish actions.
- **Do not host the upstream app unchanged.** It needs Forge-specific load/save behavior.
- **Load from existing Manager artifacts first.** The current authenticated artifact endpoint is already the right read surface for generated VTTs.
- **Save reviewed output non-destructively first.** Start with a reviewed or revisioned artifact instead of immediately overwriting the generated subtitle.
- **Manager-reviewed artifacts are the authority after human edit.** Human save should land in Manager first; CMS and Mux publishing should remain explicit downstream actions.
- **V1 launches from job detail.** Editors should start review from the existing Manager job page rather than a separate review queue.
- **Reviewed subtitles are revisioned artifacts.** Keep generated artifacts intact and save human edits as separate reviewed/revisioned artifacts so audits and rollback stay simple.
- **Publishing should be explicit.** Reuse or extend existing Mux override flow and add CMS write-back deliberately, rather than publishing on every save.
- **Package extraction is a later step.** Once the session contract is stable, Forge can decide whether to extract a reusable subtitle editor package.

## Repo Fit

- Manager already writes `transcript.json`, `subtitles.vtt`, and `subtitles-{lang}.vtt` artifacts.
- Manager already exposes authenticated artifact reads for job outputs.
- Manager already has a Mux subtitle sync/override path.
- CMS already has a `video_subtitles` model with `source: manager` and `aiGenerated` fields.
- What does not exist yet is a human-review save contract that turns edited subtitle text into a durable reviewed artifact and then publishes it intentionally.

## Open Questions

None for v1.

## Resolved Questions

- **What becomes authoritative after a human edit?** Manager-reviewed artifacts first. Human saves should update durable reviewed artifacts in Manager, and publish to CMS or Mux should happen as an explicit follow-up action.
- **Should v1 launch from job detail or a review queue?** Job detail first. This reuses the existing job/artifact context and avoids designing a separate queue before the review workflow proves out.
- **Should reviewed subtitles replace generated artifacts?** No. Store reviewed subtitles as separate revisioned artifacts and leave generated artifacts unchanged.
