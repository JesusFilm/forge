# Semantic Search Eval Harness

## Problem Frame

The **admin** semantic-search service (RRF over scene-level vector + Postgres FTS, multilingual en/es/fr, video + experience types) is in active iteration: ranking/fusion tuning, embedding/index changes, query understanding, and content-coverage work are all in flight or upcoming. (Note: this is the admin-owned search path, not the legacy CMS/Strapi one.) Today there is no way to tell whether a given change makes search better or worse — every commit is a guess. Nisal needs an on-demand harness that produces a clear, comparable "better / worse than before" signal for every change he tries, so iteration in the coming weeks is grounded in evidence rather than vibes.

## Requirements

- **R1.** A local CLI command runs the full eval suite end-to-end against a given semantic-search backend (configurable URL/env), producing a single headline result: **win-rate vs the saved baseline**, plus a per-query breakdown.
- **R2.** Test queries come from two sources: (a) **synthetic** queries generated by an LLM, with a portion generated from a user-intent perspective (e.g. "what would someone struggling with X type?") rather than only from indexed content, to mitigate corpus leakage; (b) a **growing adversarial / regression set** stored as a plain JSON/YAML file (`regressions.yaml`) committed to the repo. Anyone who spots a bad result in the wild appends an entry by hand-editing the file: `{ locale, query, notes }`. Zero tooling overhead; low friction once you know the file exists.
- **R3.** Quality is judged **pairwise**: for each query, an LLM judge sees the **top-20** results from the baseline run and from the current run side-by-side and picks the better list (or "tie"). Each pairing is run **twice with A/B swapped** to remove position bias; verdicts disagree → counted as tie. For each result the judge sees `title + snippet` as returned by the search API, with the **snippet truncated to ~200 chars** to keep prompt tokens bounded.
- **R3a.** Caveat surfaced in run output: because the judge sees the snippet returned by search, a change that _only_ improves snippet generation (not ranking) can register as a "win." This is a feature not a bug — better snippets are a real product improvement — but the run summary explicitly notes "this run improved snippets, ranking changes uncertain" when win-rate jumps without ranking changes (heuristic: most baseline result IDs still present in current results, just better-snippeted).
- **R3b.** Queries are **native-language**: synthetic queries for locale `xx` are generated in language `xx` and tested against locale `xx`. Cross-lingual query patterns (English query against non-English locale) are explicitly out of v1; can be added as a second test suite later.
- **R4.** The harness covers a **hard-coded list of the top 30 locales by labeled video count** in Core (researched 2026-05-06 via the public Core API gateway). The list is committed to the repo as a constant. This is the right size: only 20 locales have ≥50 videos and only ~30 reach ≥40 videos, so going deeper just adds queries against thin corpora.

- **R4a.** The harness exposes two run profiles: `--quick` (≈6 strong-judge locales: `en, fr, es, de, pt, ja`) for during-iteration use, and a default/full run across all 30 locales for end-of-day or pre-merge use. Same harness, same logic, different locale set.
- **R4b.** A `--locale=<bcp47>` flag targets a single locale on demand, so when a change is suspected to affect one specific language the harness can drill in without running the full set. Any bcp47 admin search accepts is allowed, even ones outside the hard-coded 30.
- **R4c.** Per-locale judge competence is a known gradient: Tier-1 (`en, fr, es, de, pt, it, nl…` — Romance/Germanic), Tier-2 (`ru, ar, fa, zh, ja, ko, hi, th, vi, id, tr` — major non-Latin), Tier-3 (`km, yue, ur, fil, te, kk, ta, ro, pl, zh-hans, pt-PT, es-ES, bn` — softer judge signal). Output reports tier per locale so a regression in Tier-3 isn't read with the same confidence as one in Tier-1.
- **R5.** A **baseline** is a committed snapshot of (queries, top-K result lists, **content fingerprint**) for a known-good state. Re-baselining is an explicit, deliberate command — never automatic — so an accepted improvement becomes the new bar.
- **R5a.** **Content fingerprint** = a small object recorded per run: `{ scene_embeddings: { count, max_updated_at }, transcript_embeddings: { count, max_updated_at }, experiences: { count, max_updated_at } }`. Captures whether admin's indexed content has changed.
- **R5b.** When current-run's fingerprint differs from baseline's, the console summary **warns loudly**: `⚠ INDEXED CONTENT DRIFTED since baseline (Δrows: scene+512, transcript+1024; latest update 3d after baseline). Net-win-rate may reflect content changes, not code. Consider re-baselining.` Does not block the run — Nisal decides whether to interpret cautiously or re-baseline.
- **R6.** A **small calibration set** (~10 queries with hand-labeled "obviously good" and "obviously bad" result lists) is run on every harness run to verify the LLM judge still agrees with humans on easy cases. If the judge fails the calibration, the run is flagged as untrustworthy.
- **R7.** Each run produces two outputs:
  - **Console summary** (live at end of run): run header (timestamp, git SHA, judge model, mode, locale count, query count) → headline **net win rate** = (wins − losses) / total, with `+` = better than baseline, `−` = worse, `0` = neutral → calibration PASS/FAIL → per-locale breakdown table (locale, tier, wins/ties/losses, net win-rate) → **top 10 regressions sorted by judge confidence** (query text, locale, tier, 1-line judge quote) → JSON file path.
  - **JSON file** (timestamped + git-SHA-tagged, e.g. `runs/2026-05-06-1430-<sha>.json`): full per-query detail — query text, locale, baseline top-K, current top-K, both A/B-swap verdicts, judge rationales, calibration results, run metadata. Machine-readable for diffing two runs.
- **R7a.** The judge returns one of **six** verdicts per pairing: `clearly-A-better | slightly-A-better | tie | slightly-B-better | clearly-B-better | both-irrelevant`. "Confidence" for sorting regressions = "clearly" verdicts rank above "slightly". A/B-swap is run on top of this and disagreements collapse to tie. `both-irrelevant` (judge says neither list contains relevant results) is **excluded from net-win-rate** (denominator drops) but reported separately as a diagnostic — high counts in a locale signal thin corpus, broken synthetic generator, or judge incompetence in that language. The three causes can be disambiguated over time by cross-referencing other signals.
- **R7b.** Headline metric is **net win rate**, not raw win rate. Net win rate = (wins − losses) / total comparisons, range `[-1, +1]`. Unambiguous on the literal "better or worse" question. Raw win/tie/loss counts are also reported for completeness.
- **R8.** The harness is **decoupled from the search service**: it talks to the **admin** semantic-search endpoint via its existing API (REST or GraphQL), with the target URL/env configurable so it works against local admin, staging admin, or prod admin without code changes. It does not call the legacy CMS/Strapi `/api/search` path.

## Success Criteria

- **Sanity:** Deliberately degrading search (e.g. randomizing ranking) produces a clearly losing win-rate (<<50%) on the next harness run.
- **Stability:** Running the harness twice against the same backend produces a win-rate near 50% (within a documented noise band, e.g. 45–55%) — anything outside that band signals judge or harness instability.
- **Sensitivity:** A known beneficial change (e.g. enriching the embedded snippet with themes/bible-refs) produces a clearly winning win-rate (>>50%).
- **Iteration loop (quick mode):** `--quick` (`en, fr, es, de, pt, ja`) completes in under ~3 minutes and costs well under a dollar per run. This is the "ran a change, want fast feedback" loop.
- **Confidence loop (full mode):** Default run across all 30 locales (top-20 results, Haiku judge, truncated snippets) completes in ~10–20 minutes and costs ~$5–15 per run. This is the "before I merge / end of day" loop. Acceptable because full runs are infrequent.
- **Locale honesty:** Per-locale win-rates are reported separately, never just averaged into a single number. A change that helps en and hurts Tagalog must be visible — not hidden by aggregation.
- **Compounding:** Every regression Nisal hits in the coming weeks is added to the adversarial set, so the harness gets stricter over time without manual upkeep.

## Scope Boundaries

- **Not v1:** CI gating, PR-blocking, or any automated runs. Strictly on-demand local CLI.
- **Not v1:** A web dashboard, leaderboard UI, or shared run history. A flat output file is sufficient.
- **Not v1:** Real user query logs / click-through evaluation. Decided against — too sparse and requires logging infra.
- **Not v1:** Hand-curated golden set. LLM-as-judge plus regression set is the chosen tradeoff.
- **Not v1:** Latency, cost, or availability metrics for the search service itself. Quality only.
- **Not v1:** Pointwise relevance scores (NDCG, precision@k). Pairwise win-rate is the only metric.

## Key Decisions

- **LLM-as-judge over hand-labeling:** Chosen for scalability and to match existing OpenRouter pipeline. Judge bias and noise are mitigated by (a) pairwise comparison (drift-resistant), (b) A/B swap, and (c) the calibration set.
- **Synthetic + adversarial queries over real-user logs:** Chosen because user-query logs are sparse and require logging infra; synthetic + adversarial compounds organically as bugs surface.
- **Pairwise win-rate over pointwise NDCG:** Pairwise directly answers "better or worse?" and stays stable across judge-model versions — pointwise scores drift when the judge changes.
- **Comparison-first, baseline-as-snapshot:** The baseline is a committed file, not "yesterday's run." Re-baselining is explicit, so improvements have to be consciously accepted.
- **Hard-coded top 30 locales in v1, with quick/full split:** Admin search supports any locale (Core has 2,303); running all ~2,300 is impractical and most have 1–2 videos — measuring quality there measures sparseness, not search. Researching Core's `labeledVideoCounts` showed only 20 locales have ≥50 videos and ~30 reach ≥40, so 30 is the natural cutoff. List is committed to the repo as a constant; refreshable on demand by re-running the Core query. Quick/full split keeps the iteration loop fast while still letting you measure breadth before merging.
- **Per-locale win-rates, never aggregate-only:** A regression that hits one language family is the exact kind of bug we want to catch, so the headline output reports per-locale win-rates. Aggregate is computed but secondary.
- **Top-K depth = 20:** Wide enough to catch ranking regressions deeper in the list, not just at positions 1–10. Drives a real cost decision (see judge model below).
- **Judge: Haiku 4.5, snippets truncated to ~200 chars:** Picks cost-controlled signal over absolute judge quality. Truncation removes most token bloat with minimal information loss (the first sentence of a snippet carries most of the relevance signal). Risk: Haiku may be less reliable on Tier-3 locales (Khmer, Cantonese, Telugu, Kazakh, Tamil). Mitigation: calibration pairwise-self-comparison runs per locale will surface any locale where Haiku drifts from ~50% on a stable backend; those locales get flagged "judge-unstable" in output, not silently averaged in.
- **Native-language queries only in v1:** Each locale's synthetic queries are generated in that locale's language. Cross-lingual (English-query-against-non-English-locale) is a real user pattern but it doubles test surface and forks the baseline; deferred to a second test suite once v1 is shipped and trusted.
- **Generic via public API:** Harness calls the existing `/api/search` or GraphQL endpoint, configurable per environment. Not a CMS-internal tool.

## Dependencies / Assumptions

- OpenRouter access (existing) for both query generation and the judge.
- Admin's semantic-search API is stable enough that the response shape doesn't change weekly. (It's actively iterating internally but the call surface — query string, locale, top-K result list — is stable.)
- For the top ~10–20 high-resource locales in the set, indexed content is dense enough and the LLM is competent enough to generate plausible native synthetic queries. For the long-tail of the top-100, native generation may degrade and fallback-to-translation is acceptable — but that fact is recorded so we don't lie about what we're testing.
- Judge model competence in a given language is a known-degraded signal; it is honestly reflected in per-locale results rather than averaged away.
