# Job Detail Enrichment Review Player

## What We're Building

Add a new review card to the manager job details page, placed below the existing
Error Log, that lets operators inspect enrichment results through a unified
Before / After surface.

The card should use the same player language as the reusable web video player
and switch both the player and the surrounding detail panel when tabs change.
`Before` means the current live Mux and CMS state for the job target. `After`
means the generated outputs from the current enrichment job. The detail panel
should focus on the operator-facing enrichment outcomes around the video:
subtitles, chapters, title, description, and related sync context when those
signals are available.

## Why This Approach

We considered three shapes:

- one unified review card with tabs that switch the player and details together
- a review player plus separate per-domain compare sections below it
- keeping comparison mostly inside existing step rows and adding only a smaller
  playback panel

The chosen approach is the first one. It matches the current product direction
for job-detail compare and override flows, gives operators one coherent place to
review the result, and keeps the page structure simple: existing summary and
step details stay intact, while the new review experience lives at the bottom as
an additive card instead of fragmenting across workflow rows.

## Key Decisions

- Bottom-of-page placement: insert the new review card below the existing Error
  Log section on the job details page.
- Unified tabs: `Before` and `After` switch both the player and the surrounding
  review details together, not just text panels.
- Live-state `Before`: the review surface should read current live Mux and CMS
  state rather than introducing a frozen job-start snapshot requirement.
- Generated `After`: the review surface should use the current job's generated
  artifacts and compare summaries as the source of truth for enriched output.
- Reuse the existing web player language: do not design a separate manager-only
  player shell when the repo already has a canonical player in `apps/web`.
- Review-first scope: this feature is for inspection and QA of enrichment
  results. Planning can decide which existing override/apply actions remain in
  step-level UI versus which belong in the new review card.
- Graceful partial data: if a domain has generated output but no live Mux or CMS
  value yet, the card should still render a useful empty-state comparison rather
  than requiring every domain to be present.

## Resolved Questions

- `Before` means the current live Mux and CMS state, not a frozen pre-job
  snapshot.
- Tab changes should update both the player and the surrounding detail card.
- The preferred product shape is one unified review card rather than separate
  domain compare panels.

## Open Questions

No product-level blockers remain for planning.

## Next Steps

Proceed to planning with the unified review-card approach and live-state
`Before` semantics as the chosen design. Planning should decide the smallest
reusable player extraction that lets manager share the web player controls
without creating a third diverging implementation.
