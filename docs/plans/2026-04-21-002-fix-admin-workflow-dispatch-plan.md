# Fix admin workflow dispatch — use `start()` from `workflow/api` instead of direct invocation

## Overview

`apps/admin` integrates the useworkflow SDK (`workflow@4.2.2`) with
`withWorkflow` wired into `next.config.ts`. The build plugin transforms
functions tagged with the `"use workflow"` directive so they must be
dispatched through the runtime via `start(...)` from `workflow/api`.
Today, two call sites invoke those functions directly, which throws at
runtime in production:

```
GraphQLError: You attempted to execute workflow runSceneEmbeddingBackfill
function directly. To start a workflow, use start(runSceneEmbeddingBackfill)
from workflow/api
```

Unit tests did not catch it because the `"use workflow"` directive is
inert outside the compiled Next.js production build — test mode runs
the functions as plain async. Smoke testing R1 against live production
surfaced the crash.

This plan routes both call sites through `start()`, adds resolver- and
service-level tests that assert the dispatch shape (not just the
workflow logic), and captures the test-mode/prod-mode divergence as a
durable learning so the next workflow-driven feature doesn't recreate
the gap.

## Problem Frame

- R1 scene-embedding backfill is the first production use of admin's
  workflow runtime. The infra shipped via PR #798 (R1) and feat-104
  (Railway provisioning). Smoke testing revealed the dispatch bug on
  2026-04-21 immediately after Redis was provisioned and the GraphQL
  route came online.
- The bug blocks every ADMIN-triggered workflow: `triggerSceneEmbeddingBackfill`
  mutation (R1 smoke) AND experience-embedding regeneration on publish
  (latent — no one has hit it yet because no experience has been
  published in prod).
- The fix is mechanically small. The depth comes from closing the
  test-mode/prod-mode observability gap so the class of bug stops
  recurring.

## Requirements Trace

- **R1.** `triggerSceneEmbeddingBackfill` GraphQL mutation executes
  successfully end-to-end against the self-hosted workflow runtime in
  production. Callers receive the existing `SceneEmbeddingBackfillReport`
  shape (or a typed error), not `GraphQLError: Unexpected error.`
- **R2.** `experience.service.ts::regenerateEmbedding` (line 476)
  dispatches `runExperienceEmbedding` via the same pattern. Latent bug
  fixed in the same PR.
- **R3.** Dispatch is verified by tests that would have caught this
  bug — i.e., they assert `start()` from `workflow/api` is called with
  the right workflow function and args, not that the workflow function's
  internals run correctly (that's already covered).
- **R4.** A short learning doc captures the "test-mode/prod-mode
  workflow-directive divergence" pattern so future workflow integrations
  add dispatch-level assertions by default.

## Context & Research

### Relevant code and patterns

- `apps/admin/next.config.ts` — `withWorkflow(nextConfig, { workflows: { dirs: ["src/workflows"] } })`. Plugin confirmed wired; scan restricted to `src/workflows` per documented OOM guard.
- `apps/admin/src/workflows/sceneEmbeddingBackfill.ts:85` — `runSceneEmbeddingBackfill`, `"use workflow"`.
- `apps/admin/src/workflows/experienceEmbedding.ts:30` — `runExperienceEmbedding`, `"use workflow"`.
- `apps/admin/src/graphql/mutations/scene-embedding.ts:34` — **bug site 1**: direct call.
- `apps/admin/src/services/experience.service.ts:476` — **bug site 2**: direct call in `regenerateEmbedding` path.
- `apps/admin/src/app/.well-known/workflow/v1/{flow,step,webhook}/route.js` — self-hosted runtime (generated by the build plugin; do not hand-edit). Confirms admin is its own workflow host; dispatch target is the same origin.
- `apps/admin/package.json` — `"workflow": "^4.2.2"`.
- `apps/manager/next.config.ts` — **does NOT** have `withWorkflow` wrapped; its `"use workflow"` functions still run inert. Manager is therefore NOT a dispatch-pattern reference; admin is the first app with a live runtime in this monorepo.

### SDK API (from `workflow@4.2.2` type definitions)

Verified in `node_modules/.pnpm/@workflow+core@4.2.2.../dist/runtime/start.d.ts` and `runtime/run.d.ts`:

- `start(workflow, args, options?): Promise<Run<TResult>>` — `args` is an array matching the workflow function's parameter tuple.
- `Run<T>` exposes:
  - `runId: string`
  - `get returnValue: Promise<TResult>` (polls the runtime until complete; returns the workflow's final value)
  - `get status`, `cancel()`, `getReadable()`, etc.
- Synchronous-shaped callers do: `await (await start(fn, [args])).returnValue`.

- `docs/solutions/best-practices/parallel-workflow-error-robustness-20260420.md` — R1's `Promise.allSettled` + typed-error classification pattern. Unrelated to dispatch but relevant if the fix needs to surface workflow-level errors to GraphQL callers cleanly.

### Why no external research

Admin is the ONLY app in this monorepo using the workflow runtime live. Manager has the package but not `withWorkflow`. All dispatch patterns are derivable from the SDK's bundled type definitions + the generated runtime route files. External research would add nothing the local SDK source doesn't already tell us.

## Key Technical Decisions

- **Preserve synchronous mutation shape** by awaiting `run.returnValue`. Rationale: caller contract doesn't change; no downstream Pothos / codegen churn; matches the implicit expectation of feat-104's smoke plan ("returns a typed report"). Tradeoff acknowledged in Risks.
- **Do NOT set `WORKFLOW_API_KEY`.** Admin self-hosts the runtime via same-origin `/.well-known/workflow/v1/*` routes. The HMAC secret (already set) signs internal webhook→step calls; no external cloud service is used.
- **Fix both call sites in one PR.** Atomic, single concept. Splitting them would leave a latent crash waiting for the first experience publish.
- **Test the DISPATCH, not just the workflow.** New tests mock `start()` from `workflow/api` and assert it was called with the expected workflow function + args. The existing workflow logic tests (510 from PR #798) stay untouched — they still exercise the function body in inert mode.
- **Document the test-mode/prod-mode divergence** in `docs/solutions/best-practices/` as a durable pattern note. Any future workflow feature must include dispatch-level tests on top of workflow-body tests.

## Open Questions

### Resolved during planning

- **Does `start()` require `WORKFLOW_API_KEY`?** No — verified by the self-hosted route files + `WORKFLOW_HMAC_SECRET` already being set. Env audit shows no `WORKFLOW_API_KEY` is needed for same-origin dispatch.
- **Does manager have a working dispatch pattern to copy?** No. Manager's `next.config.ts` lacks `withWorkflow`. Admin is the first app with a live runtime. Use the SDK types + admin's own generated runtime as reference.
- **Does `start()` accept the arg object or arg array?** Array. Signature: `start(fn, [argObject])`. The workflow function's single-argument shape becomes `args: [argObject]` at the call boundary.
- **Does the mutation's return contract need to change?** No — `Run.returnValue` lets us preserve the existing `SceneEmbeddingBackfillReport` return shape.

### Deferred to implementation

- **Exact test double for `start()`** — Vitest `vi.mock("workflow/api", ...)` vs module-boundary factory injection. Decide while writing the test; both work, the minor preference depends on how existing admin tests handle external-module mocks.
- **Whether `Run.returnValue` surfaces a typed error or a rejected promise on workflow failure.** The SDK docs imply rejection; confirm empirically when writing the error-path test. Affects whether the resolver needs a try/catch wrapper for typed GraphQL error masking.
- **Whether to also add a GraphQL-level integration test that exercises the live module registry** — `apps/admin/src/app/.well-known/workflow/v1/flow/route.js` is generated at build time. Testing against the built output is heavy and platform-dependent. Defer; the dispatch unit tests catch the specific regression class.

## High-Level Technical Design

> _This illustrates the intended approach and is directional guidance for review, not implementation specification. The implementing agent should treat it as context, not code to reproduce._

```
┌──────────────────────────────┐
│ GraphQL resolver /           │
│ service method               │
│                              │
│   await start(               │   ← new boundary: dispatch via SDK
│     runWorkflow,             │     instead of direct call
│     [args],                  │
│   ).then(r => r.returnValue) │   ← preserves synchronous shape
└────────────┬─────────────────┘
             │ POSTs HMAC-signed
             ▼
┌──────────────────────────────┐
│ /.well-known/workflow/v1/    │   ← self-hosted runtime
│ {flow,step,webhook}          │     (generated by withWorkflow,
│                              │      do not hand-edit)
│   runtime dispatches steps,  │
│   persists state, returns    │
│   final return value via     │
│   polling (Run.returnValue)  │
└──────────────────────────────┘
```

Caller contract unchanged. Dispatch boundary moves from "direct
function call" to "SDK `start()` → self-hosted runtime → polled
`returnValue`." No change to `"use workflow"` function bodies or their
unit tests.

## System-Wide Impact

- **Interaction graph:** GraphQL mutation → workflow runtime (new); experience service regenerate path → workflow runtime (new). Both were previously in-process async. No external interaction graph change.
- **Error propagation:** `Run.returnValue` rejection surfaces as a thrown error in the resolver, which Yoga masks in prod. Same terminal UX as today; internal path slightly longer. If the workflow crashes mid-run (durable-retry path), the `returnValue` poll resolves with the workflow's own retry decision — defer verification to Unit 1 test writing.
- **State lifecycle risks:** Workflow runs are now durable — state lives in the runtime's storage. A crashed mutation request retries the workflow? No — `start()` creates one run; if the CLIENT retries the mutation, a second run is dispatched. Callers are ADMIN-authored operator tools today (no client retries). Acceptable. Document in the runbook.
- **API surface parity:** Only these two call sites exist. A grep for other direct invocations of any `apps/admin/src/workflows/*` export into non-workflow files is part of Unit 1 verification — if any show up, they're part of this PR.
- **Integration coverage:** Dispatch unit tests + the learning doc; no live integration test (intentionally — see Deferred Questions). Real coverage comes from R1 smoke after the coreId-mapping S3 refactor lands separately.

## Risks & Dependencies

- **Long backfill blocks the GraphQL request.** `Run.returnValue` polls until complete. A full-catalog scene backfill could take minutes-to-hours. That matches the pre-fix behavior (direct call also blocked), but it's worth flagging: Railway's default HTTP proxy timeout is generous (~600s) but not infinite. **Mitigation for now:** smoke runs always pass a small `coreIds` filter (typically 1 video = seconds). **Mitigation for full backfill:** a later PR changes the mutation to return `{ runId }` immediately and adds a `sceneEmbeddingBackfillRun(runId)` query that reads `Run.returnValue` on demand. Out of scope for this fix.
- **Dispatch tests depend on stable `workflow/api` module shape.** The SDK is pinned `^4.2.2`. A major-version bump would require revisiting the helper. Acceptable — version bumps are intentional events.
- **Manager's inert state is now anomalous.** With admin correct, the next team member glancing at manager's workflows may assume they also dispatch via `start()`. They don't, because `withWorkflow` isn't wired. **Mitigation:** the learning doc explicitly notes manager is still inert and lists that as a follow-up ticket for whoever gets to manager's durability.

## Documentation / Operational Notes

- Admin CLAUDE.md "Scene embeddings" section already mentions the runbook's need to invoke via GraphQL. Add a one-liner noting "mutation dispatches via workflow/api; runs as a durable workflow run in the admin-hosted runtime" so future readers don't assume the in-process model.
- No env var changes. No Railway redeploy needed beyond the normal post-merge deploy. No migration.
- Rollback: single-commit revert is safe — the two call sites just go back to their current broken shape. Since they're already broken in prod, rollback is only relevant if the fix introduces worse behavior, which is hard to imagine for a 2-line change.
