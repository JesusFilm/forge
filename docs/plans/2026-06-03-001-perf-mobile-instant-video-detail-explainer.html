Make the video screen feel instant.

Today, tapping a search result stalls behind a blank spinner for up to 5 seconds. This plan makes the screen paint the moment you tap — and start playing from data the app already has in hand.

✕

The premise that broke the mental model: the content isn't local. Every tap is a cold network fetch of a huge GraphQL query to production admin — and the search result's title, image, and playback ID are thrown away on the way to the detail screen.

The diagnosis

Three things make it slow

None of them are "the local CMS is slow," because there is no local CMS. The bottleneck is a blocking, oversized network fetch with no reuse of data the app already held.

01

Every tap is a cold network fetch

Mobile reads from the production admin GraphQL API. The Apollo cache is in-memory only — empty on every cold start. Nothing is bundled or persisted.

One enormous blocking query

The screen waits for the full WatchVideo fragment — every image, every locale, all sibling videos, every dub with every download and subtitle track — before showing anything.

Key technical decisions

The eight calls that shape it

Each one was stress-tested by adversarial review. Several started as something more complex and got simpler.

KTD1Seed data, not a faster query, solves the spinner▸

First paint and playback come from the seed the caller already holds. This kills the spinner on its own and is independent of any query work — everything else just makes the canonical data arrive fast.

KTD2One query with partial data — never two on the same field▸

Two queries against the same videoBySlug root field fight over the cache slot and lose fields ("Cache data may be lost"). Instead: keep one query, turn on returnPartialData, and let seed + cache stream fields in as they arrive.

KTD3A faster lean fetch is a deferred admin handoff, not this plan▸

A genuinely smaller network request needs a new server field — out of scope. Perceived speed is carried by seed + warm cache, not a faster fetch. A latency probe can decide whether to file that follow-up, but its outcome can't change what this plan builds.

KTD4The session owns the seed→core→complete machine▸

The shared session establishes a stable identity once, field-merges later updates, and guards the defaults with userHasChosen* flags — so enrichment can never reset a language or subtitle a user picked mid-load.

KTD5Decide the playback swap by playbackId, not URL strings▸

The stored hls URL isn't guaranteed byte-identical to the seed-built URL for the same asset. Comparing extracted playback IDs means the same asset never triggers a reload, and a genuinely different variant takes exactly one accepted swap.

KTD6Validate only the synthesized URLs; trust canonical ones▸

Seed URLs come from untrusted nav params, so they're host-allowlisted. The canonical hls passes through unchanged — gating it through the Mux-only allowlist would break real media served from other JFP hosts.

KTD7Hand-rolled persistence, gated above the Apollo provider▸

The standard cache-persist library is incompatible with our Apollo version and crashed launch before. This is hand-rolled: restore above the provider, time-bounded so a slow read can't freeze startup, an incremental snapshot (no synchronous extract on backgrounding), version + TTL, and signed/expiring URLs excluded.

KTD8No app-wide cache normalization in this plan▸

Normalizing every shared entity bought nothing once persistence switched to result trees — while risking the homepage. It was cut to a scoped follow-up, keeping this plan's blast radius on the watch flow.

What could break

Risks & mitigations

Surfaced by a deepening pass and an adversarial review. The persistence layer carries history — it crashed launch once before.

Persistence relaunch crash highest risk

A prior persist attempt crashed launch. Mitigated: hand-rolled, gated above the provider, best-effort guarded, time-bounded read, real-device verification.

Synchronous flush on backgrounding crash class

A full cache extract on the kill-prone background transition janks low-end Android. Mitigated: incremental snapshot — background does only a tiny write.

Selection-reset race correctness

Re-publishing the video could wipe a mid-load language pick. Mitigated: stable identity + userHasChosen guards.

"Rare swap" wasn't rare playback

Device locale can resolve a different default variant. Mitigated: compare playbackId; same asset never swaps, others take one accepted swap.

Expiring URLs go stale data

Persisting signed download URLs guarantees future 404s. Mitigated: volatile URLs excluded from the snapshot; always re-fetched.

Slow restore freezes startup cold start

An above-provider gate blocks the whole app. Mitigated: 300–500ms read timeout → boot cold, discard a late restore.

Security threat model

Three untrusted surfaces

This work introduces nav-param input and on-device persistence — so it names the surfaces explicitly rather than assuming the API is the only boundary.

⌥

Deep-link seed injection

A crafted universal link could supply a malicious seed — a non-Mux stream host, an arbitrary image host, an oversized payload.

MitigationDecode validates seed stream + image URLs against host allowlists; returns null on malformed input.
⊗

Cache-poisoning persistence

A bad or stale entity persisted during a brief API issue could survive restarts and resurface.

MitigationVersion key + short TTL eviction, volatile-URL exclusion, and cache-and-network revalidation on view.
↯

Download path traversal

The local filename is derived from an untrusted download URL by splitting on slashes.

MitigationValidate the download URL and strip path separators from the derived filename before writing.
