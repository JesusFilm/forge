# fix: Resolve Mux source language correctly for snapshot enrichment

## Overview

The snapshot-backed enrichment flow currently passes the first selected coverage language value directly into stage clone creation. In the coverage UI, those values are CMS language core IDs such as `3934`, not Mux-generated subtitle language codes such as `ru`.

As a result, the manager ends up asking Mux to generate subtitles with the wrong language hint. Our current Mux helper falls back to `"en"` for unknown values, which produced the observed Russian QA failure where generated subtitles were mostly `[NON-ENGLISH SPEECH]`.

This fix should resolve the selected CMS source language into the correct Mux code before creating the stage asset, and fall back to `auto` instead of `en` when the mapping is missing or unsupported.

## Problem Statement / Motivation

The current stage-clone QA flow is doing two different language jobs with one field:

- the coverage UI tracks selected languages using CMS/core language IDs
- Mux `generated_subtitles[].language_code` expects a constrained set of codes:
  - `en`, `es`, `ru`, etc.
  - or `auto`

Today the path is:

1. coverage UI sends `languages: ["3934"]`
2. `/api/enrich` passes `languages[0]` into `createStageCloneForJob(...)`
3. `stageClone.ts` forwards that value to `createMuxAsset(...)`
4. `mux.ts` normalizes unknown values to `"en"`

That is wrong for non-English source videos.

The behavior we want is:

1. identify the intended source language from CMS data
2. convert that language into a valid Mux generated-subtitle language code when possible
3. if no safe mapping exists, ask Mux to detect it with `auto`

This keeps subtitle generation robust for QA while avoiding accidental English forcing.

## Research Summary

### Internal Findings

- `/api/enrich` currently parses `languages` as opaque strings and passes `languages[0]` into `createStageCloneForJob(...)` unchanged.
- `coverage-report-client.tsx` sends `selectedLanguageIds`, which are CMS language IDs, not BCP-47 or Mux codes.
- `stageClone.ts` currently uses `preferredSourceLanguage` for two distinct purposes:
  - choosing the preferred video variant by matching `variant.language.coreId`
  - forwarding the same raw value as `subtitleLanguageCode`
- `mux.ts` only accepts the supported Mux generated-subtitle codes and otherwise defaults to `"en"`.
- `languages` data exposed by `apps/manager/src/app/api/languages/route.ts` currently includes only:
  - `id`
  - labels
  - country/continent metadata
- The manager therefore has no explicit language metadata layer for Mux resolution today.

### External Mux Findings

Mux generated subtitles accept a bounded set of language codes, not arbitrary CMS IDs.

From the official asset-create API:

- `inputs[].generated_subtitles[].language_code`
- possible values include:
  - `en`, `es`, `it`, `pt`, `de`, `fr`, `pl`, `ru`, `nl`, `ca`, `tr`, `sv`, `uk`, `no`, `fi`, `sk`, `el`, `cs`, `hr`, `da`, `ro`, `bg`
  - `auto`
- `auto` lets Mux detect the spoken language automatically

References:

- [Mux API: Create an asset](https://www.mux.com/docs/api-reference/video/assets/create-asset)
- [Mux guide: Auto-generated captions and transcripts](https://www.mux.com/docs/guides/add-autogenerated-captions-and-use-transcripts)

## Proposed Solution

Add an explicit source-language resolution layer for snapshot enrichment.

### High-Level Approach

1. Keep the coverage UI request shape unchanged for now.
2. In `/api/enrich`, treat `languages[0]` as a CMS language ID, not a Mux code.
3. Resolve that CMS language ID into manager-side language metadata from CMS.
4. Convert that metadata into a valid Mux generated-subtitles code.
5. If the language is not mappable or not supported by Mux, pass `auto`.
6. Continue using the original CMS language ID for:
   - preferred variant selection
   - job record `languages`
   - downstream manager UI labeling

This keeps the UI contract stable while fixing the Mux integration boundary.

## Technical Considerations

### 1. Separate “CMS source language ID” from “Mux subtitle language code”

We need two distinct values in the flow:

- `preferredSourceLanguageId`
  - CMS/core language ID such as `3934`
  - used to choose the best matching source variant
- `muxSubtitleLanguageCode`
  - one of the supported Mux codes or `auto`
  - used only when creating the stage Mux asset

The current code conflates those values.

### 2. Resolve Mux language from CMS language metadata, not from user-facing labels

Do not derive the Mux code from display labels such as `"Russian"` or `"Русский"`.

Instead, prefer structured language metadata from CMS such as:

- `bcp47`
- `iso3`
- or another canonical language-code field if available

If CMS already stores `bcp47`, the conversion should be straightforward:

- `ru` or `ru-RU` → `ru`
- `en-US` → `en`

If the normalized code is not supported by Mux, use `auto`.

### 3. `auto` is a safer fallback than `"en"`

The current `"en"` fallback biases unknown languages toward incorrect English transcription.

For this QA flow, `auto` is safer because:

- it avoids forcing the wrong ASR language
- it gives Mux a chance to detect supported non-English speech
- it degrades better for mixed or unknown-language content

### 4. Keep variant selection logic independent from Mux language mapping

`stageClone.ts` currently sorts variants by `variant.language.coreId`.
That behavior is still useful and should stay based on CMS language identity, not Mux codes.

So the stage-clone API should evolve from:

```ts
createStageCloneForJob(video, sourceLanguage)
```

to something more explicit, such as:

```ts
createStageCloneForJob(video, {
  preferredSourceLanguageId,
  muxSubtitleLanguageCode,
})
```

This reduces future confusion and makes the callsite self-documenting.

### 5. Avoid broad UI/API churn unless needed

The narrowest useful fix likely does not require changing the coverage request payload.

Instead, `/api/enrich` can:

- read `languages[0]` as the selected source language ID
- look up the matching language metadata from CMS
- resolve the Mux code server-side

This keeps the browser behavior stable and concentrates the fix at the backend boundary where it belongs.

### 6. Persist the resolved Mux language on the job for QA visibility

To make QA and debugging easier, record the resolved value in `job.artifacts.materialization`, for example:

```ts
{
  preferredSourceLanguageId: "3934",
  resolvedMuxSubtitleLanguageCode: "ru"
}
```

or:

```ts
{
  preferredSourceLanguageId: "3934",
  resolvedMuxSubtitleLanguageCode: "auto"
}
```

That makes it obvious whether a bad subtitle result came from:

- wrong CMS selection
- wrong mapping
- unsupported language
- or Mux ASR quality itself

## Dependencies & Risks

### Dependencies

- Existing CMS language metadata must expose enough structured language-code information to derive a Mux code cleanly
- Existing stage-clone flow in:
  - `apps/manager/src/app/api/enrich/route.ts`
  - `apps/manager/src/services/stageClone.ts`
  - `apps/manager/src/services/mux.ts`

### Risks

- Some CMS languages may not have reliable `bcp47` or similar metadata populated
- Some CMS languages may normalize to valid BCP-47 roots that Mux still does not support
- `auto` may still produce imperfect results for noisy or mixed-language videos

### Mitigations

- Centralize the mapping logic in one helper with explicit tests
- Prefer deterministic direct mappings when available
- Use `auto` only as the fallback path, not the primary path for known supported languages
- Persist the resolved code for fast QA debugging
