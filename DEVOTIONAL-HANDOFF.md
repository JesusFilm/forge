## 6. Mastra workspaces — что это на самом деле

Источник: https://mastra.ai/docs/workspace/overview.md

**Это не способ организации проекта и не про монорепо.** Workspaces — runtime-возможность
для агентов: постоянное окружение, в котором у агента есть файловая система, запуск
shell-команд, семантический обход кода, индексированный поиск и переиспользуемые
skill-инструкции.

```typescript
import { Workspace, LocalFilesystem, LocalSandbox } from '@mastra/core/workspace'

const workspace = new Workspace({
  filesystem: new LocalFilesystem({ basePath: './workspace' }),
  sandbox: new LocalSandbox({ workingDirectory: './workspace' }),
  skills: ['skills'],
})
```

- требует `@mastra/core@1.1.0`+ — здесь `1.36.0`, поддерживается
- назначается глобально на инстанс Mastra (все агенты наследуют) либо на отдельного агента
- `filesystem` и `mounts` взаимоисключающие
- `mastra.shutdown()` уничтожает зарегистрированные workspaces
- в `apps/mastra/src` сейчас ни одной ссылки на workspaces нет (совпадение в
  `repo-root.ts` — про pnpm workspace, это другое)

**Применимость к этой задаче — решить до переноса.** Текстовые агенты (modernizer, критики,
point-picker) — это LLM-вызовы через `createDevotionalLlm`; ни файлы, ни shell им не нужны.
Workspaces становятся осмысленны, если цель — чтобы **агент сам** читал кеш девоушналов,
запускал рендер и оценивал результат, то есть работал циклом. Это заметно другая архитектура,
чем текущая (чистые функции + кеш-каталог как сериализуемый шов между sub-workflow, потому что
байты аудио не переживают границу шага workflow).

Если решение — давать агентам руки, то `basePath` должен указывать на `devo/`, и это надо
проектировать вместе с текущим кешем, а не поверх него. План миграции стоит прогнать через
`/ce-code-review` — он затронет `apps/mastra/CLAUDE.md`.
